# Validation checklist для Workflow Kit

Используй этот чеклист, чтобы проверить черновик на реальном или тестовом изменении.

## 1. Проверка структуры

- [ ] Change workspace создан в `ai/specs/YYYYMMDD_HHMM_change-name/`.
- [ ] Есть `spec.md`.
- [ ] Есть `plan.md`.
- [ ] Есть `scope.md`.
- [ ] Есть `tasks.md`.
- [ ] После `tasks` есть заготовка `verification.md`, после реализации она заполнена результатами.
- [ ] Опциональные файлы (`research.md`, `data-model.md`, `implementation-fix.md`) созданы только если нужны.

## 2. Проверка `spec.md`

- [ ] Документ остаётся читаемым Markdown, без JSON/XML/YAML-обёртки всего spec.
- [ ] Понятно, зачем нужно изменение.
- [ ] Понятно, что должно стать правдой после изменения.
- [ ] Формат требований/кейсов подходит задаче: правила, сценарии, таблицы, flow, examples или edge cases.
- [ ] Проверяемые пункты действительно тестируемые/проверяемые.
- [ ] Есть критерии успеха.
- [ ] Есть out-of-scope.
- [ ] Неясности помечены `ТРЕБУЕТ УТОЧНЕНИЯ`.
- [ ] Spec отвечает на WHAT/WHY, а не HOW.
- [ ] В spec нет implementation details: файлов, классов, функций, библиотек, архитектурных решений и пошаговой реализации.

## 3. Проверка `plan.md`

- [ ] План отвечает на P0/обязательные требования или явно выбранный текущий scope.
- [ ] Есть список новых файлов.
- [ ] Есть список изменяемых файлов.
- [ ] Есть стратегия тестирования.
- [ ] Есть риски и митигации.
- [ ] Нет скрытого расширения scope.
- [ ] `scope.md` создан или обновлён как часть plan.

## 4. Проверка `scope.md`

- [ ] Есть `Freely editable`.
- [ ] Есть `Requires confirmation`.
- [ ] Есть `Forbidden`.
- [ ] Config/public API/migrations/shared files не попали в freely editable случайно.
- [ ] Агенту понятно, что делать с файлом, которого нет в списках.

## 5. Проверка `tasks.md`

- [ ] Все задачи имеют `[Txxx]`.
- [ ] Все задачи имеют checkbox.
- [ ] Каждая задача содержит путь к файлу, команду или проверяемый результат.
- [ ] Задачи достаточно маленькие.
- [ ] P0 задачи идут раньше P1/P2.
- [ ] Есть финальная задача на проверки/verification.
- [ ] Порядок выполнения понятен.
- [ ] Параллельные задачи помечены `[PAR]`, а не неоднозначной короткой меткой `P`.

## 6. Проверка implementation behavior

- [ ] Агент прочитал `spec.md`, `plan.md`, `scope.md`, `tasks.md` перед правками.
- [ ] Агент выбрал первую незавершённую задачу или указанную задачу.
- [ ] Агент не менял files outside scope без подтверждения.
- [ ] Агент отметил `[x]` только после проверки или явного объяснения.
- [ ] При blocker агент остановился, а не додумал рискованное решение.

## 7. Проверка `verification.md`

- [ ] Зафиксированы команды и результаты.
- [ ] Зафиксированы ручные проверки или причина их отсутствия.
- [ ] Зафиксированы gaps/risks.
- [ ] Есть итоговое решение: Ready / Ready with warnings / Blocked / Needs user decision.

## 8. Красные флаги

Если видишь это — workflow надо править:

- [ ] Агент спрашивает процесс заново, хотя skill должен был объяснить.
- [ ] `scope.md` не помогает принять решение о правке файла.
- [ ] `tasks.md` превратился в крупные vague пункты.
- [ ] Verification выглядит как декоративная отписка.
- [ ] Маленькая правка требует слишком много документов.
- [ ] Большая правка всё равно теряет контекст.

## Решение после валидации

```markdown
## Failed / friction
- ...

- ...

- [ ] Simplify
- [ ] Add missing artifact/rule
- [ ] Split skill
- [ ] Not viable
```
