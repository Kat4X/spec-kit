# Спецификация Workflow Kit

## Контекст

Workflow Kit нужен как лёгкая альтернатива тяжёлым spec-frameworks. Цель — получить воспроизводимый AI workflow через skills и Markdown-файлы, не строя сразу CLI, registry, schema engine и интеграции со всеми агентами.

## Цели

- Зафиксировать единый процесс от идеи до проверенной реализации.
- Хранить состояние работы в файлах, а не в чате.
- Дать агенту понятные stop conditions.
- Предотвратить расползание scope и случайные правки чужих файлов.
- Сделать workflow переносимым между проектами через project rules.

## Не-цели

- Не заменять код specs как CodeSpeak.
- Не строить полный OpenSpec-клон с archive/sync/schema engine на MVP.
- Не навязывать один стек, директории исходников или test runner.
- Не коммитить рабочие артефакты автоматически.

## Пользователи

### U1: Разработчик с AI-агентом
Хочет дать агенту изменение и получить контролируемую реализацию без потери контекста.

### U2: Агент
Нуждается в явных артефактах, границах редактирования, задачах и проверках.

### U3: Ревьюер / будущий владелец проекта
Хочет понять, почему изменение было сделано именно так.

## User stories

### US-1: Создать спецификацию изменения [P0]
Как разработчик,
я хочу превратить идею в `spec.md`,
чтобы согласовать что и зачем строим до кода.

Критерии приёмки:
- [ ] КОГДА идея неоднозначна ТО агент задаёт короткие уточняющие вопросы или фиксирует безопасные предположения в релевантной секции.
- [ ] КОГДА создаётся `spec.md` ТО в нём понятным способом описаны контекст, суть изменения, требования/кейсы, out-of-scope и open questions.
- [ ] КОГДА требование критично и неясно ТО оно помечено `ТРЕБУЕТ УТОЧНЕНИЯ`, а не выдумано молча.
- [ ] КОГДА user stories не подходят задаче ТО агент использует правила, таблицы, flows, examples или другой ясный формат.

### US-2: Создать технический план [P0]
Как разработчик,
я хочу получить `plan.md` и `scope.md`,
чтобы агент понимал как делать и какие файлы можно менять.

Критерии приёмки:
- [ ] КОГДА есть неразрешённые критичные вопросы ТО план не создаётся без решения.
- [ ] КОГДА план создан ТО он перечисляет новые и изменяемые файлы.
- [ ] КОГДА план создан ТО рядом создан или обновлён `scope.md` с границами редактирования.
- [ ] КОГДА изменение может затронуть shared/public/config files ТО они попадают в `scope.md` как requiring confirmation или forbidden.

### US-3: Разбить план на задачи [P0]
Как агент,
я хочу иметь `tasks.md` с маленькими задачами,
чтобы реализовывать изменение пошагово и проверяемо.

Критерии приёмки:
- [ ] КОГДА создаётся задача ТО она имеет ID `[T001]`, checkbox и явный файл/проверяемый результат.
- [ ] КОГДА задача относится к user story ТО она помечена `[US-1]`.
- [ ] КОГДА задачу можно делать независимо ТО она помечена `[PAR]`.

### US-4: Реализовать задачу безопасно [P0]
Как агент,
я хочу выполнять первую незавершённую задачу,
чтобы не прыгать по контексту и не ломать порядок.

Критерии приёмки:
- [ ] КОГДА задача зависит от невыполненной задачи ТО агент останавливается.
- [ ] КОГДА изменение требует файла вне allowed scope ТО агент спрашивает подтверждение.
- [ ] КОГДА проверка не запускалась ТО задача не отмечается выполненной без явного объяснения.

### US-5: Верифицировать изменение [P0]
Как разработчик,
я хочу иметь `verification.md`,
чтобы видеть чем доказано, что изменение работает.

Критерии приёмки:
- [ ] КОГДА проверка прошла ТО записаны команда, результат и дата/контекст.
- [ ] КОГДА проверка не может быть запущена ТО записана причина и риск.
- [ ] КОГДА есть warnings/failures ТО есть решение: fix now, accept risk, or ask user.

### US-6: Отличать ошибку spec от ошибки реализации [P1]
Как разработчик,
я хочу не искажать spec ради бага кода,
чтобы намерение оставалось чистым.

Критерии приёмки:
- [ ] КОГДА desired behavior изменилось ТО меняется `spec.md`.
- [ ] КОГДА spec верна, но код ошибся ТО создаётся implementation fix task/note.

## Функциональные требования

- FR-001: Workflow Kit SHALL хранить артефакты изменения в `ai/specs/YYYYMMDD_HHMM_change-name/` по умолчанию.
- FR-002: Workflow Kit SHALL поддерживать этапы `specify`, `plan`, `tasks`, `implement`, `verify`.
- FR-003: Workflow Kit SHALL иметь шаблоны для `spec.md`, `research.md`, `plan.md`, `data-model.md`, `scope.md`, `tasks.md`, `implementation-fix.md`, `verification.md`.
- FR-004: `spec.md` SHALL быть чистым Markdown без JSON/XML/YAML-обёртки всего документа.
- FR-005: Workflow Kit SHALL требовать явные границы редактирования в `scope.md` до implementation.
- FR-006: Workflow Kit SHALL запрещать отмечать задачу выполненной без проверки или объяснения, почему проверка невозможна.
- FR-007: Workflow Kit SHOULD поддерживать delta-секции поведения в `spec.md` для brownfield changes.
- FR-008: Workflow Kit MAY позже получить CLI-команды, но MVP работает без CLI.

## Нефункциональные требования

- NFR-001: Инструкции должны быть пригодны для разных проектов, без привязки к Android/Yutori.
- NFR-002: Workflow должен быть достаточно лёгким для личных проектов.
- NFR-003: Все шаблоны должны быть Markdown-readable без специальных инструментов.
- NFR-004: Процесс должен позволять остановиться и спросить человека вместо рискованной автоправки.

## Вне скоупа MVP

- Автоматическая валидация Markdown.
- CLI для создания/статусов/архивации.
- Полный OpenSpec-style archive/sync.
- Генерация кода из specs как в CodeSpeak.
- Поддержка marketplace/community schemas.

## Открытые вопросы

- [ ] Насколько подробным должен быть минимальный `scope.md` для маленького локального change?
- [ ] Нужен ли отдельный `workflow-kit-research` skill или research достаточно встроить в plan?
- [ ] Нужно ли делать `ai/specs/` дефолтом или разрешить проекту переопределять workspace path?
