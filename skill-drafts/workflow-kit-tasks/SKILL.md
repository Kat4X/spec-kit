# Workflow Kit: tasks

Создай задачи реализации для изменения: `$ARGUMENTS`.

Цель: создать self-contained `tasks.md` для следующего AI-этапа `workflow-kit-implement`. Tasks должны превратить технический план в маленькие, проверяемые и упорядоченные шаги реализации без написания кода на этом этапе.

Не пиши код на этапе tasks.

## Порядок работы

### 1. Найди workspace

Найди workspace, созданный `workflow-kit-specify` и заполненный `workflow-kit-plan`:

- если `$ARGUMENTS` — путь к workspace, используй его;
- если `$ARGUMENTS` — `change-name`, найди `ai/specs/*_{change-name}/`;
- если совпадений несколько — выбери последний по timestamp или уточни;
- если workspace не найден — остановись и попроси путь или точный `change-name`.

В workspace должны быть:

- `spec.md`;
- `plan.md`;
- `scope.md`.

Если любого из них нет — остановись: tasks нельзя честно создать без spec, plan и scope.

### 2. Проверь шаблоны

Перед созданием файлов проверь доступность обязательных шаблонов:

- `template/TASKS-TEMPLATE.md` — для `tasks.md`;
- `template/VERIFICATION-TEMPLATE.md` — для `verification.md`.

Если нужный шаблон недоступен — остановись и сообщи, какой шаблон отсутствует. Не создавай артефакты из памяти или резервной структуры.

### 3. Прочитай контекст

Прочитай:

- `spec.md`;
- `plan.md`;
- `research.md`, если есть;
- `data-model.md`, если есть;
- `scope.md`;
- project instructions, если они не были в контексте и влияют на задачи.

Не используй старые `ai/specs/*`, `plan.md` или `tasks.md` из других workspaces как источник требований для этого change, если пользователь явно не указал связанный workspace.

### 4. Проверь готовность plan

Перед декомпозицией проверь:

- `plan.md` помечен как готовый к `workflow-kit-tasks` или не содержит явных блокеров;
- блокирующих `ТРЕБУЕТ УТОЧНЕНИЯ` из `spec.md`/`plan.md` не осталось; продуктовые/рискованные вопросы нужно вернуть пользователю до создания `tasks.md`;
- `scope.md` существует и соответствует файлам/поверхностям из `plan.md`;
- задачи не требуют файлов из `Forbidden`.

Если есть блокер — остановись и скажи, что нужно закрыть до `tasks.md`.

### 5. Разбей plan на задачи

Задачи пишутся для AI-исполнителя. Каждая задача должна быть однозначной без доступа к этому диалогу.

Правила:

- Каждая задача занимает примерно 15–60 минут работы.
- Каждая задача имеет checkbox и ID `[T001]`, `[T002]`, ... без пропусков.
- Каждая задача содержит явный путь к файлу, команду или проверяемый результат.
- Обязательные/P0 требования идут раньше optional/P1/P2.
- Тестовые задачи ставь рядом с кодом, который они проверяют, а не только в конце.
- Не создавай задачи на файлы из `Forbidden`.
- Если задача требует `Requires confirmation`, пометь её `[CONFIRM]` и укажи, что именно нужно подтвердить.
- Если задачу можно делать параллельно после выполнения зависимостей, пометь её `[PAR]`.
- Не добавляй задачи, которых нет в `plan.md`, если это не явно нужная проверка или подготовка.
- Не превращай tasks в микрошаги уровня “открыть файл” или “прочитать функцию”.
- Финальная фаза обязательно включает запуск проверок, запись результата в `verification.md` и проверку выхода за границы из `scope.md`.

Формат задачи:

```text
- [ ] [T001] [P0] [Case-1] Описание с явным путём/командой/результатом
```

Дополнительные метки:

- `[P0]`, `[P1]`, `[P2]` — приоритет requirement/scope;
- `[PAR]` — можно делать параллельно с другими `[PAR]` задачами той же фазы;
- `[CONFIRM]` — перед implementation нужно подтверждение пользователя;
- `[US-1]`, `[Case-1]`, `[R-001]`, `[NFR-001]` — связь с требованием из `spec.md`.

### 6. Создай `tasks.md`

Используй `template/TASKS-TEMPLATE.md` как единственный источник структуры `tasks.md`.

Правила заполнения:

- Сохраняй верхнеуровневые секции шаблона, их названия и порядок.
- Удали HTML comments и placeholders.
- Каждую фазу делай цельной: подготовка, фундамент, реализация requirements, тесты/интеграция, финальная верификация.
- Если user stories/cases/rules из `spec.md` имеют ID, используй эти ID в задачах.
- Если точный файл неизвестен, задача должна явно ссылаться на область поиска из `plan.md`, а не придумывать путь.
- Если задача зависит от другой, отрази это в фазе или в `## Порядок выполнения`.

### 7. Создай `verification.md`

Если `verification.md` отсутствует — создай его по `template/VERIFICATION-TEMPLATE.md`.

Если `verification.md` уже есть — не затирай существующие результаты; обнови только ссылки/заготовки, если это безопасно.

### 8. Проверь качество

Перед финалом проверь:

- [ ] `tasks.md` покрывает обязательные требования из `spec.md` и технический подход из `plan.md`.
- [ ] Все planned files из `plan.md` покрыты задачами или явно не нужны.
- [ ] Все P0/обязательные acceptance criteria покрыты задачами и проверками; если блокер остался, `tasks.md` не создан.
- [ ] Нет задач на файлы из `Forbidden`.
- [ ] Tasks, требующие `Requires confirmation`, помечены `[CONFIRM]`.
- [ ] Есть финальная верификация и запись результата в `verification.md`.
- [ ] Задачи достаточно маленькие для AI-исполнителя, но не превращены в шумные микрошаги.
- [ ] `tasks.md` самодостаточен для `workflow-kit-implement`.

### 9. Git и `.gitignore`

Нельзя добавлять в git файлы или директории, которые игнорируются `.gitignore`, без явного разрешения пользователя. Не используй `git add -f` для workflow artifacts.

Перед `git add`/commit проверь созданные и изменённые артефакты одним из способов:

```bash
git check-ignore -v -- <path>
git status --short --ignored
```

Политика коммита:

- Не выполняй `git add`, commit или push без явного запроса пользователя.
- Если пользователь попросил подготовить commit, добавляй только не ignored workflow artifacts (`tasks.md`, `verification.md`) и сначала проверь `.gitignore`.
- Если workspace находится в ignored-директории, не добавляй его в git и явно скажи в финале: `не закоммичено, потому что путь игнорируется .gitignore`.
- Временные анализы, черновики и exploratory-артефакты не коммить без явного запроса.

### 10. Результат

Если `tasks.md` создан, в финале покажи:

- путь к workspace;
- путь к `tasks.md`;
- путь к `verification.md`;
- всего задач;
- сколько P0/обязательных задач;
- сколько `[PAR]` задач;
- есть ли `[CONFIRM]` задачи и какие;
- рекомендуемую первую задачу;
- готовность к `workflow-kit-implement`: да/нет;
- если не готово к `workflow-kit-implement` — что нужно закрыть;
- статус git/commit или причину, почему артефакты не добавлены.

Если остановилась до создания `tasks.md`, в финале покажи:

- почему tasks нельзя честно создать сейчас;
- блокирующие вопросы или отсутствующие шаблоны;
- что будет следующим шагом после ответа пользователя;
- явно укажи: `tasks.md` не создан.
