# Spec Kit: plan

Создай технический план для изменения: `$ARGUMENTS`.

Цель: создать self-contained `plan.md` для следующего AI-этапа `spec-kit tasks`. Plan должен перевести WHAT/WHY из `spec.md` в технический HOW: подход, файлы, контракты, тестирование, риски и границы редактирования.

Не пиши код на этапе plan.

## Порядок работы

### 1. Найди workspace

Найди workspace, созданный `spec-kit specify`:

- если `$ARGUMENTS` — путь к workspace, используй его;
- если `$ARGUMENTS` — `change-name`, найди `ai/specs/*_{change-name}/`;
- если совпадений несколько — выбери последний по timestamp или уточни;
- если workspace не найден — остановись и попроси путь или точный `change-name`.

В workspace должен быть `spec.md`. Если его нет — остановись: plan нельзя честно создать без spec.

### 2. Проверь шаблоны

Перед созданием файлов проверь доступность обязательных шаблонов:

- `assets/PLAN-TEMPLATE.md` — для `plan.md`;
- `assets/SCOPE-TEMPLATE.md` — для `scope.md`.

Опциональные шаблоны используй только если соответствующий артефакт нужен:

- `assets/RESEARCH-TEMPLATE.md` — для `research.md`;
- `assets/DATA-MODEL-TEMPLATE.md` — для `data-model.md`.

Если нужный шаблон недоступен — остановись и сообщи, какой шаблон отсутствует. Не создавай артефакты из памяти или резервной структуры.

### 3. Прочитай spec и текущие границы

Прочитай:

- `spec.md`;
- `scope.md`, если он уже есть;
- `research.md`, если он уже есть;
- project instructions, если они не были в контексте и влияют на план;
- README/project docs и минимально релевантный код;
- существующие тесты и конфиги, если они важны для технического подхода.

Не используй старые `ai/specs/*`, `plan.md` или `tasks.json` как источник требований для этого change, если пользователь явно не указал связанный workspace.

### 4. Разреши открытые вопросы и технические неизвестные

Найди в `spec.md` все `ТРЕБУЕТ УТОЧНЕНИЯ`.

Для каждого вопроса:

- если ответ можно найти в коде, документации или существующих паттернах — исследуй и зафиксируй ответ в `research.md` по `assets/RESEARCH-TEMPLATE.md`;
- если вопрос продуктовый, рискованный или требует решения пользователя — остановись и спроси пользователя до создания `plan.md`;
- если вопрос не блокирует plan — зафиксируй безопасное техническое предположение в `research.md` или `plan.md`.

Также создай `research.md`, если перед планом нужен выбор между техническими вариантами, проверка существующих паттернов или фиксация важного ограничения.

Если research не нужен — не создавай `research.md`.

### 5. Спроектируй решение

План должен покрывать обязательные требования из `spec.md`. P1/P2 включай только если они явно в scope текущего change или пользователь попросил.

Определи:

- технический подход;
- архитектуру или поток управления/данных;
- новые и изменяемые файлы;
- public/shared surfaces: API, schema, migrations, config, generated files, shared data;
- данные и состояние;
- стратегию тестирования;
- безопасность, приватность и производительность, если применимо;
- риски и митигации;
- что требует подтверждения перед implement.

Следуй существующим паттернам проекта. Не добавляй новые зависимости, слои или архитектурные решения без явной причины и записи в рисках/решениях.

Пиши plan так, чтобы следующий AI мог сгенерировать `tasks.json` без доступа к этому диалогу.

### 6. Создай или обнови `scope.md`

`scope.md` — обязательный артефакт перед `spec-kit tasks` и `spec-kit implement`.

Если `scope.md` уже есть — обнови его, если план меняет границы редактирования или выявляет новые public/shared surfaces.

Если `scope.md` нет — создай его по `assets/SCOPE-TEMPLATE.md` как единственному источнику структуры.

Для маленького локального change делай `scope.md` коротким, но не пропускай его: укажи конкретные freely editable файлы/пути, ожидаемые requires confirmation поверхности и явное правило для неуказанных файлов.

### 7. Создай `data-model.md`, если применимо

Создавай `data-model.md` только если change добавляет или меняет:

- persistent data model;
- database schema / migration;
- file format;
- external contract shape;
- state model, который важен для реализации и тестов.

Используй `assets/DATA-MODEL-TEMPLATE.md` как единственный источник структуры.

Если data model не меняется — не создавай `data-model.md`; укажи в `plan.md`, что отдельная модель данных не требуется.

### 8. Создай `plan.md`

Используй `assets/PLAN-TEMPLATE.md` как единственный источник структуры `plan.md`.

Правила заполнения:

- Plan отвечает на HOW, но не превращается в tasks: не расписывай пошаговую реализацию по микрозадачам.
- Каждое обязательное требование из `spec.md` должно иметь техническое покрытие или явный блокер.
- Файлы перечисляй конкретно, если они известны; если точный файл ещё не установлен, укажи область поиска и почему.
- Public/shared surfaces явно помечай как требующие подтверждения или осторожной реализации.
- Не оставляй placeholders и HTML comments в итоговом `plan.md`.

### 9. Проверь качество

Перед финалом проверь:

- [ ] `plan.md` покрывает обязательные требования `spec.md`.
- [ ] Блокирующих `ТРЕБУЕТ УТОЧНЕНИЯ` не осталось; продуктовые/рискованные вопросы возвращены пользователю до создания `plan.md`.
- [ ] Research создан, если были технические неизвестные.
- [ ] Data model создан только если применим.
- [ ] `scope.md` создан или обновлён и задаёт понятные границы редактирования.
- [ ] Новые/изменяемые файлы перечислены или честно ограничены областью поиска.
- [ ] Тестовая стратегия есть.
- [ ] Риски и подтверждения явно отмечены.
- [ ] Plan самодостаточен для `spec-kit tasks`.
- [ ] Нет лишних технологий, слоёв и scope creep.

### 10. Git

Артефакты plan — локальные workflow artifacts. Не добавляй их в git, не создавай commit и не используй `git add -f`. Push на этом этапе не выполняй.

### 11. Результат

Если `plan.md` создан, в финале покажи:

- путь к workspace;
- путь к `plan.md`;
- путь к `research.md`, если создан;
- путь к `data-model.md`, если создан;
- путь к `scope.md`;
- краткий технический подход;
- список новых/изменяемых файлов;
- основные риски и что требует подтверждения;
- готовность к `spec-kit tasks`: да/нет;
- если не готово к `spec-kit tasks` — что нужно закрыть;
- что workflow artifacts оставлены локально и не добавлены в git.

Если остановилась до создания `plan.md`, в финале покажи:

- почему plan нельзя честно создать сейчас;
- путь к `research.md`, если он был создан до остановки;
- блокирующие вопросы или отсутствующие шаблоны;
- что будет следующим шагом после ответа пользователя;
- явно укажи: `plan.md` не создан.
